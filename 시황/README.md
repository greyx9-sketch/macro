# 매크로 지표 자동 수집 대시보드

미국·한국 거시지표 17종을 매일 자동으로 수집해 대시보드로 보여준다.

→ **https://greyx9-sketch.github.io/macro/**

## 엑셀과의 관계

`매크로 머티리얼.xlsm` 은 **어떤 지표를 볼지에 대한 명세**였다. 재현해야 할 원본이 아니다.
그래서 값의 기준은 언제나 권위 있는 소스(FRED · 한국은행 ECOS)이지, 엑셀이 아니다.
엑셀에서 가져온 것은 다음 둘뿐이다.

- **과거 예측(컨센서스)** — ForexFactory 가 지난 주를 주지 않아 다른 출처가 없다.
- **ISM PMI 과거 실제값** — 라이선스 문제로 FRED 에 없어 다른 출처가 없다.

그 밖의 엑셀 실제값은 전부 제거했다. 자동 소스가 훨씬 깊은 이력을 갖고 있는데
날짜 규약과 조정 기준이 달라 계열이 조용히 오염됐기 때문이다(아래 참조).

## 빠른 시작

```bash
# 1. API 키 발급 (무료)
#    FRED : https://fredaccount.stlouisfed.org/apikeys   (즉시)
#    ECOS : https://ecos.bok.or.kr/api/                  (승인까지 최대 1일)
set FRED_API_KEY=발급받은키
set ECOS_API_KEY=발급받은키

# 2. 엑셀 과거 데이터 백필 (최초 1회)
python scripts/import_excel.py "C:\Users\greyx\Desktop\매크로 머티리얼.xlsm"

# 3. 매핑이 맞는지 검증
python scripts/verify.py
python scripts/verify.py --bls    # 원 통계기관(BLS) 과 직접 대조 — 키 불필요, IP 당 25회/일
python scripts/verify.py --stale  # 갱신이 멈춘 계열 찾기 — 값의 정오가 아니라 '들어오고 있는가'

# 4. 수집 + 화면용 JSON 생성
python scripts/collect.py
python scripts/export_json.py

# 5. 확인
python -m http.server 8000 -d site     # http://localhost:8000
```

ISM 역사를 메우려면(최초 1회, 약 8분):

```bash
python scripts/backfill_ff_weeks.py --from 2020-01 --dry-run   # 먼저 확인
python scripts/backfill_ff_weeks.py --from 2020-01
```

필수 외부 패키지는 **없다**. `playwright` 는 CDS 5년물과, ForexFactory 평문 요청이
Cloudflare 에 막혔을 때의 대체 경로에만 쓰인다. 둘 다 없어도 나머지는 수집된다.

## 데이터 출처

엑셀에 적혀 있던 investing.com 링크 15개는 전부 폐기했다.
공개 API 가 없고, Cloudflare 봇 차단이 걸려 있으며, 이용약관이 자동 수집을 금지한다.
그 위에 만들면 반드시 깨진다.

| 구분 | 지표 | 출처 | 상태 |
|---|---|---|---|
| 물가 | CPI 지수 / CPI YoY / PPI 지수 / PCE YoY / 근원 PCE YoY / **근원 PCE MoM** | FRED | 완전 자동 |
| 고용 | NFP / 실업률 / 시간당 임금 / 신규 실업수당 / JOLTS / **고용비용지수 QoQ** | FRED | 완전 자동 |
| 경기 | **실질 GDP QoQ / 소매판매 MoM** | FRED | 완전 자동 |
| 서베이 | ISM 제조업·서비스업 PMI | ForexFactory 캘린더 | 자동 (FRED 에 없음) |
| 서베이 | **미시간대 소비자심리** | FRED | 완전 자동 |
| 금융 | 미 기준금리 / 10Y-2Y | FRED | 완전 자동 |
| 금융 | 한국 기준금리 | 한국은행 ECOS | 완전 자동 |
| 금융 | 미·한 CDS 5년물 | worldgovernmentbonds (headless) | 취약 — 아래 참조 |
| 전 지표 | **예측(컨센서스)** | ForexFactory 캘린더 | 자동, 단 과거 백필 불가 |

총 22종. 굵게 표시한 6종은 **캘린더 원본에 이미 들어오고 있는데 쓰지 않던 것들**이다
(원본 186건 중 9건만 쓰고 있었다). 예측은 캘린더가 주고 실제값만 FRED 로 붙였다.

### 컨센서스에 대해 반드시 알아야 할 것

`https://nfs.faireconomy.media/ff_calendar_thisweek.json` 는 **이번 주만** 준다.
`lastweek` / `nextweek` / `thismonth` 는 전부 404다. 즉:

- 한 주를 놓치면 그 주의 예측값을 **공식 피드로는** 복구할 수 없다.
- 그래서 워크플로가 하루 두 번 돌고, 매핑 성공 여부와 무관하게
  원본 이벤트를 `calendar_events` 테이블에 **전량 먼저** 저장한다.
  나중에 매핑이 틀렸다고 밝혀져도 `calendar_ff.remap_from_stored()` 로 복구할 수 있다.

무료 컨센서스가 없는 지표: CPI 지수·PPI 지수(지수 레벨 예측은 제공 안 함),
PCE YoY(m/m 만 제공), 10Y-2Y·CDS(원래 예측이 없는 지표), 한국 기준금리(피드에 KRW 없음).
엑셀도 이 중 상당수는 예측이 비어 있었다.

### 그 피드는 **실제값을 주지 않는다**

오랫동안 몰랐던 사실이고, 이것 때문에 ISM 2종이 **처음부터 한 번도 자동 수집되지
않았다.** 실측:

```
ff_calendar_thisweek.json   99건 중 actual 이 있는 것 0건
ff_calendar_thisweek.xml    <actual> 엘리먼트 자체가 없음
ff_calendar_thisweek.csv    동일
```

예고용 피드라 예측·이전만 준다. 대부분의 지표는 실제값을 FRED 에서 받으므로 문제가
없었는데, **ISM 은 라이선스 정책상 FRED 에 없다**(`fred_id=None`). 즉 ISM 의 유일한
실제값 경로가 실제값을 주지 않는 피드였다. 관측치 22건은 전부 엑셀 백필이었고,
8/03 에 발표된 7월 제조업 PMI 는 며칠이 지나도 `actual: null` 이었다.

무료 대안을 전부 시험했다.

| 후보 | 결과 |
|---|---|
| FRED (`NAPM` 등) | 계열 없음. ISM 이 2016년 제공 중단 |
| DBnomics `ISM/pmi` | 값이 헤드라인 PMI 가 아님. `nm-pmi` 는 2025-08 에서 멈춤 |
| Trading Economics guest | `HTTP 410 — guest account has been discontinued` |
| Nasdaq Data Link | Incapsula 봇 차단 |
| econdb · fxstreet | `HTTP 401` 인증 필요 |
| ismworld.org | SSO 로그인 페이지로 리다이렉트 |

남은 하나가 **캘린더 웹페이지**다. 응답 안에 `window.calendarComponentStates[N]` 이 있고
그 `days` 배열이 공식 피드의 상위집합이다 — `actual` 과 `revision` 까지 들어 있다.
`fetchers/calendar_ff_html.py` 가 이걸 읽는다.

파서를 믿을 근거는 두 가지다.

- 같은 응답의 신규 실업수당 청구 `199K` == FRED `ICSA` 의 `2026-08-01, 199000`
- `?week=jul6.2026` 의 ISM 서비스업 `54.0 / 54.2 / 54.5`
  == 엑셀 백필 `2026-06` 의 실제·예측·이전 **세 값 모두 일치**

**이것은 공식 피드를 대체하지 않는다.** 예측·이전의 주소스는 계속 JSON 피드이고,
HTML 은 빈 칸만 메운다. 한 값을 두 소스가 각자 계산하기 시작하면 언젠가 갈린다.

그리고 `?week=mmmD.yyyy` 로 **과거 주를 돌려준다**(2020-03 까지 확인). 위의
"공식 피드로는 복구할 수 없다" 에 단서가 붙는 이유다 — `scripts/backfill_ff_weeks.py`
가 월 첫 두 주만 골라 받아 ISM 역사를 메운다. 백필은 **빈 칸만 채운다**(`fill_only`).
엑셀에서 온 발표 당시 컨센서스를 지금 렌더링된 값으로 바꿔치기하면
서프라이즈 계산이 통째로 흔들리기 때문이다.

#### 스크레이핑이라는 사실을 숨기지 않는다

ForexFactory 앞에는 Cloudflare 가 있다 — `robots.txt` 조차 챌린지를 돌려준다.
그래서 3단으로 두고, **막힌 것을 성공으로 세지 않는다.**

```
1) 평문 GET  →  2) Playwright 렌더링(cds.py 와 같은 패턴)  →  3) ok=False 로 명확히 실패
```

차단 판정은 좁게 잡아야 한다. 처음에 `challenge-platform` 을 마커로 넣었다가
**멀쩡한 응답을 전부 차단으로 오판했다** — 그 문자열은 Cloudflare 가 모든 페이지에
심는 수동 탐지 스크립트 경로라 정상 페이지에도 늘 있다. 지금은 인터스티셜에만 나오는
`cf_chl_opt` / `Just a moment...` 만 보고, 진짜 성공 판정은
**데이터 블롭이 실제로 있는가**로 한다.

### 「실제」와 「이전」은 같은 종류의 숫자가 아니다

표에서 두 값이 어긋나 보이는 것은 버그가 아니라 **출처가 다르기 때문**이다.
이걸 모르면 표가 자기모순처럼 읽힌다.

| | 실제 | 이전 |
|---|---|---|
| 출처 | FRED/ECOS 수준값 | 컨센서스 피드(ForexFactory·엑셀) |
| 시점 | **현재 개정치** | **발표 당시 값** |
| 정밀도 | 전체 (0.2673%) | 헤드라인 자릿수로 반올림 (0.2%) |

시간당 임금 2026-06 행은 `실제 0.35% / 이전 0.30%` 인데 바로 아랫줄 `실제` 는 0.27% 다.
0.27% 는 BLS 가 지금 공표하는 값이고, 0.30% 는 그때 발표됐던 값(연간 계절조정 재추정 전)이다.
둘 다 맞다. 그래서 화면은 이렇게 나눈다.

- **`이전` 은 발표 당시 값 그대로** 둔다. 시장이 그때 본 숫자를 버리면 안 된다.
  현재 계열값과 달라졌으면 셀에 `↻` 를 달고 툴팁에 두 값을 함께 보여준다.
- **`이전대비` 는 우리 계열끼리** 뺀다 (`실제[M] − 실제[M−1]`, 달력 기준 조회).
  출처가 다른 두 숫자를 빼면 발표된 변화도, 우리 계열의 변화도 아닌 값이 나온다.
- **서프라이즈는 컨센서스와 같은 자릿수로 맞춘 뒤** 뺀다. 예측이 0.1%p 단위인데
  실제값을 전체 정밀도로 빼면 **없는 서프라이즈가 생긴다** — 위 2026-06 은
  발표값도 예측도 둘 다 0.3% 였는데 `+0.05%p 예상 상회`로 표시되고 있었다.
  비율 계열 발표의 24~36% 가 이 경우였다. 반올림 전 값은 툴팁에 남는다.

`실제` 값 자체는 원 통계기관과 직접 대조해 확인한다 — `verify.py --bls` 참조.
BLS 공개 API v1 은 키가 필요 없는 대신 **IP 당 하루 25회**다. 한도를 넘으면
'값이 다르다'가 아니라 **'물어보지 못함'** 으로 보고하고 종료 코드 3 을 낸다 —
못 물어본 것과 물어봤더니 달랐던 것은 다른 결론이므로 섞지 않는다.

### CDS 가 취약한 이유

worldgovernmentbonds 페이지는 값이 전부 `data-async-variable=…>----</span>` 플레이스홀더인
클라이언트 렌더링이고, 내부 `wp-json/common/v1/historical` 은 nonce 없이 403 이다.
따라서 Playwright 로 실제 렌더링해야 한다.

수집기는 페이지가 내부적으로 부르는 historical 응답을 가로채 **전체 이력**을 얻는다
(한국 2007년~ 5,061건, 미국 2017년~ 3,254건). 가로채기가 실패하면 렌더링된 DOM 에서
최신값 1건만 읽는 2순위 경로로 내려간다. 둘 다 실패해도 나머지 16종 수집은 정상 완료되고
대시보드 신선도 패널에 실패가 표시된다. 값이 조용히 덮어써지는 일은 없다.

참고: 엑셀(investing.com)과 worldgovernmentbonds 는 같은 CDS 를 하루씩 다른 날짜에
붙이는 경향이 있다. worldgovernmentbonds 가 훨씬 깊은 이력을 주므로 겹치는 구간은
그쪽으로 통일된다. 이 교체는 `revisions` 에 기록되지 않는다(위 약속 4).

### 이 폴더를 통째로 옮겨도 되는 이유, 그리고 옮길 때 꼭 봐야 할 것

**파이썬은 손댈 필요가 없다.** 모든 경로가 `__file__` 기준이라
(`core/db.py`·`core/store.py`·`scripts/*.py` 의 `sys.path.insert`)
폴더가 통째로 움직이면 안쪽 상대관계가 그대로다. `site/` 내부 참조도 전부 상대경로다.
**공개 URL 도 폴더 깊이와 무관하다** — Pages 아티팩트의 루트가 `site/` 이기 때문이다.

**대신 세 곳은 사람이 직접 고쳐야 한다. 셋 다 틀려도 에러가 안 난다.**

| 고칠 곳 | 왜 |
|---|---|
| `.gitignore` · `.gitattributes` | 슬래시가 든 패턴은 **그 파일이 있는 디렉터리에 고정**된다. 이 둘이 이 폴더 안에 있으므로 `data/…` 로 적는다. 밖으로 빼면 `시황/data/…` 로 바꿔야 하고, 안 바꾸면 SQLite 가 조용히 커밋되고 CSV 줄바꿈이 매번 뒤집힌다 |
| `.github/workflows/시황-수집.yml` | 워크플로는 저장소 루트에서 도므로 **거기서 본 경로**를 쓴다 (`working-directory: 시황`, `path: 시황/site`) |
| 이 문서들 | README·HANDOFF 의 명령은 이 폴더에서 실행하는 전제다 |

확인 명령은 「검증」 절에 있다.

### 왜 SQLite 가 아니라 CSV 를 커밋하는가

처음에는 `macro.sqlite` 를 커밋하려 했다. 그런데 CDS 전체 이력(8,300건)을 받고 나니
파일이 3.3 MB 가 됐고, **git 은 바이너리를 델타 압축하지 못해 커밋마다 전체 복사본을 저장한다.**
하루 두 번 × 1년이면 수백 MB 가 쌓인다.

CSV(합계 1.4 MB)로 저장하면 하루치 변경이 몇 줄 diff 로 남고, 무엇보다

```bash
git log -p data/observations.csv     # 사람이 읽는 수정치 감사 로그
```

가 성립한다. '개정 추적'이라는 원래 목표가 여기서 실제로 완성된다.
DB 가 비어 있으면 `db.connect()` 가 CSV 에서 자동 복원하므로, 저장소를 새로 클론하거나
Actions 러너처럼 매번 빈 상태로 시작해도 그대로 이어서 돌아간다.

### 검증이 실제로 잡아낸 것

만들면서 검증기가 잡아낸 버그들이다. 셋 다 **값이 단위 범위 안이라 눈으로는 안 보였다.**

| 버그 | 증상 | 잡은 방법 |
|---|---|---|
| 임포터가 옆 블록 열 침범 | 미국 CDS 36.85bp 가 10Y-2Y 의 '이전' 으로 들어감 | 단위 범위 검사 |
| vintage 조회 미동작 | `releases.actual` 이 한 번도 FRED 로 채워지지 않음 | 소스별 건수 집계 |
| 최초발표 수준값 차분 | NFP 2010-01 = -1,383천명 (정답 -6천명) | 발표값↔관측치 교차검증 |
| 새 변환(qoq) 미등록 | 고용비용지수 발표값 101건 중 52건이 빈 값 | 지표별 빈 값 비율 집계 |
| 대조표가 SA/NSA 를 혼동 | CPI 29건 중 26건 불일치 | BLS 원 수준값 독립 대조 |
| 서로 다른 정밀도끼리 뺄셈 | 발표값·예측이 둘 다 0.3% 인데 `+0.05%p 상회` | 컨센서스 해상도 대비 서프라이즈 분포 |
| ISM 이 처음부터 수집 안 됨 | 관측 22건이 전부 엑셀, 자동 수집분 0건 | 계열별 `updated_at` 최신값 집계 |
| 실패 메시지에 API 키 노출 | 공개 사이트에 ECOS 인증키가 그대로 | 수집 실패 배너를 추적하다 발견 |

세 번째가 가장 위험했다. 벤치마크 개정을 사이에 둔 두 수준값을 차분하면
실재하지 않는 숫자가 나오는데, NFP 로 그럴듯한 크기라 범위 검사에 걸리지 않았다.

네 번째는 **같은 실수를 목록이 두 군데 있어서 반복한** 경우다.
`qoq` 를 `core/transform.py` 에 추가하고 `fetchers/fred.py` 가 따로 들고 있던
목록에는 등록하지 않아, 최초발표값 경로가 1개짜리 목록으로 전분기비를 계산하다
전부 `None` 이 됐다. 지금은 그 목록이 변환 정의와 같은 파일에 있고,
등록되지 않은 변환을 만나면 조용히 `None` 을 만드는 대신 예외를 던진다.
그래서 **발표값과 관측치를 교차 대조하는 검사**를 넣었다.
개별 시점이 아니라 **위반 비율**로 판정하는 것이 핵심이다 —
계산 경로가 틀리면 거의 전 시점이 어긋나지만(437건 중 436건),
진짜 큰 개정은 소수다(2020년 실업수당은 702천건까지 벌어졌으나 1,908건 중 5건).

다섯 번째는 위 넷과 성격이 다르다. **검사 자신이 틀렸는데 그것을 검사가 잡았다.**
`verify.py --bls` 의 대조표에 CPI 를 계절조정 계열(`CUSR0000SA0`)로 적었는데
우리 `cpi_index` 는 의도적으로 계절조정 전(`CPIAUCNS`)이다. 29건 중 26건이
어긋나면서 바로 드러났다 — 계열 선택이 조금이라도 다르면 즉시 티가 난다는 뜻이고,
그것이 이 대조를 FRED 가 아닌 원 통계기관에 붙인 이유다.

여섯 번째는 값이 아니라 **비교 기준**의 문제였다. 자세한 것은
[「실제」와 「이전」은 같은 종류의 숫자가 아니다](#실제와-이전은-같은-종류의-숫자가-아니다) 참조.

일곱 번째는 **어떤 검사도 잡지 못했다.** 위의 검사는 전부 '들어온 값이 말이 되는가' 를
보는데, ISM 은 값이 아예 안 들어왔고 그건 아무도 안 보고 있었다. 사람이 계열별
`updated_at` 을 집계해 보고서야 드러났다. 그래서 [정체 감지](#값이-틀린-게-아니라-안-들어올-때)를
넣었다 — 이제 이건 검사가 잡는다.

여덟 번째는 검사가 아니라 **사용자 신고**로 시작됐다. 사이트에 뜬 수집 실패 배너를
추적하다 그 배너 문구 자체가 인증키를 담고 있는 것을 발견했다. 일시적 타임아웃 하나가
훨씬 큰 문제를 드러낸 셈이다.

### 설계상의 네 가지 약속

1. **결측은 `NULL`, 0 이 아니다.** 미발표와 "0%"를 절대 섞지 않는다.
2. **조용한 실패 금지.** 수집이 실패하면 직전 값을 유지하고 화면에 stale 배지를 띄운다.
3. **한 소스의 실패가 다른 소스를 막지 않는다.** 부분 실패 시 종료 코드는 0이다.
4. **개정과 출처 교체를 구분한다.** `revisions` 에는 *같은 소스가* 같은 기준시점의 값을
   바꾼 것만 남는다. 소스를 갈아탄 것(엑셀 CDS → worldgovernmentbonds)은 개정이 아니다 —
   구분하지 않으면 감사 로그가 출처 차이로만 가득 차 쓸모가 없어진다.
5. **안 들어오는 것도 본다.** 아래 참조. 2번의 '조용한 실패 금지' 는 *수집이 실패했을 때*
   만 다뤘는데, ISM 은 수집이 **성공했다고 보고하면서** 값이 안 들어왔다.

### 값이 틀린 게 아니라 안 들어올 때

ISM 2종이 두 달 동안 멈춰 있었는데 어떤 검사에도 안 걸렸다. 그때까지의 검사는 전부
'들어온 값이 말이 되는가' 만 봤기 때문이다 — 범위·급변·발표값↔관측치 대조. 안 들어온
것을 보는 눈이 없었다.

`core/validate.py:check_staleness` 가 그 눈이다. 날짜 차이를 그대로 쓰면 안 된다:

| 지표 | 최신 기준시점 | 오늘과의 차이 | 실제 상태 |
|---|---|---|---|
| JOLTS | 2026-06 | 67일 | **정상** — 설계상 2개월 지연 발표 |
| 미시간대 | 2026-06 | 67일 | **멈춤** — 당월 발표인데 7월분이 없다 |

같은 숫자가 정반대를 뜻한다. 그래서 지표별 `ref_lag_months` 를 빼고 **몇 주기 밀렸는지**
로 센다. 위 표는 각각 0.2주기와 2.2주기가 되어 갈린다.

임계는 2주기다. 1주기는 정상 구간이다 — 월간 지표는 그 달 발표가 나기 전까지 늘 1주기
뒤에 있다. 빡빡하게 잡으면 매번 울리고, 매번 울리는 경보는 아무도 안 본다.

발표 예정일 추정(`estimate_next_release`)에 기대지 않는 것이 중요하다. 그건 과거 발표일
표본이 있어야 하는데 ISM 은 발표일이 전부 엑셀에서 온 월 단위라 표본이 0이다 —
**가장 망가진 계열이 정확히 그 감지기의 사각지대**였다. 주기는 언제나 알고 있으므로
주기로만 판정한다.

```bash
python scripts/verify.py --stale     # 멈춘 계열이 있으면 종료 코드 1
```

화면에는 경보일 때만 적는다(`2.2개월째 갱신 없음`). 밀린 정도를 늘 적으면 카드 20장이
'1.2개월' 을 달고 있게 되어 진짜 신호가 묻힌다.

### 실패 메시지에 비밀값을 담지 않는다

수집 실패 메시지는 `fetch_log.csv` 로 커밋되고 `dashboard.json` 을 거쳐 **공개 사이트**
까지 간다. 실제로 한국은행 ECOS 인증키가 이 경로로 새어 나갔다 — 타임아웃 메시지에
URL 전체가 들어 있었고, ECOS 는 키를 쿼리가 아니라 **경로 세그먼트**에 넣는다.

```
https://ecos.bok.or.kr/api/StatisticSearch/{KEY}/json/kr/1/10000/...
```

가리는 지점을 두 곳에 둔다.

- `fetchers/base.py:_safe_url` — 쿼리의 `api_key`·`token` 류와, **호스트별 경로 규칙**.
  경로 마스킹을 일반화하지 않는다. 아무 경로나 가리면 오류 메시지를 읽을 수 없게 되어
  디버깅용으로 남기는 의미가 사라진다.
- `core/db.py:log_finish` → `core/secrets.py:safe_message` — 저장 직전 마지막 관문.
  환경변수에 든 키 문자열이 보이면 통째로 지운다. URL 마스킹이 놓치는 경로
  (서드파티 예외 메시지, 응답 본문 조각, 앞으로 추가될 소스)를 한 번 더 막는다.

### `<button>` 은 콘텐츠를 세로 중앙에 놓는다

카드가 한 줄에 넷씩 놓이는데 제목 높이가 제각각이었다. 실측:

| 카드 | cardTop | height | titleTop |
|---|---|---|---|
| CPI 지수 | 449 | 211 | **474** |
| CPI (% YoY) | 449 | 211 | **464** |
| PPI 지수 | 449 | 211 | **489** |
| PCE (% YoY) | 449 | 211 | **464** |

박스는 완전히 같은데 제목이 25px 계단을 이룬다. 원인은 `.card` 가 `<button>` 이라는
것이다 — 브라우저는 버튼 콘텐츠를 세로 중앙에 놓고, 그 규칙은 `display: block`
으로 **끊기지 않는다.** 카드마다 내용 높이가 달라(맥락 줄 없음 / 칩 한 줄)
남는 높이가 위아래로 갈리면서 제목이 내려간 것이다.

```
.card { display: flex; flex-direction: column; }   /* was: block */
.spark { margin-top: auto; }                       /* 발밑을 바닥에 붙인다 */
```

`margin-top: auto` 가 없으면 제목만 맞고 발밑 줄이 제각각이 된다.
**한 줄의 모든 카드가 제목은 위에서, 발밑은 아래에서 맞아야 한다.**

이것은 앞서 「최근 발표」 목록을 subgrid 로 고친 것과 **같은 부류**다 —
어느 쪽이든 원인은 "행마다 격자가 따로 계산된다" 였다. 주차 묶음도 같은 이유로
그룹별이 아니라 목록 전체가 한 격자다.

### 다음 발표 시점은 **날짜가 아니라 구간**으로 말한다

ForexFactory 는 이번 주치만 준다. 22종 중 확정 일정이 있는 것은 7종뿐이고
나머지는 비어 있었다 — 소비자가 가장 먼저 묻는 질문에 답이 없었던 셈이다.

이력에서 규칙을 뽑아 메우되, **날짜를 콕 집지는 않는다.** '몇 번째 무슨 요일' 규칙을

| 실업률 | 8/01 ~ 8/11 (22/24) | 8/07 | 적중 |
| 비농업 고용 | 8/01 ~ 8/15 (22/24) | 8/07 | 적중 |
| JOLTS | 7/29 ~ 8/09 (22/24) | 8/04 | 적중 |

말하지 않는 편이 나은 경우에는 침묵한다 — 표본이 8회 미만이거나(ISM 2종),
구간 폭이 21일을 넘으면(PPI 34일·소매판매 30일·PCE 27일) 표시하지 않는다.
`8월 중` 보다 나을 게 없기 때문이다. 다만 **화면에서까지 침묵하지는 않는다** —
`다음 발표일 미정` 이라고 적고 이유를 팁에 붙인다. 빈 칸으로 두면 수집이 고장난
것처럼 보이는데, 실제로는 우리가 규칙을 못 찾은 것이다.

`매 영업일 갱신`(10Y-2Y·CDS 2종)과 `정책회의에서 결정`(연준·한은)도 같은 이유로
구분해 적는다. 셋 다 「다음 발표」가 비어 있지만 **비어 있는 이유가 다르다.**

#### 확정이 언제나 이기는 것은 아니다

확정 일정이 오면 그쪽이 이긴다 — 단, **날짜까지 알 때만** 그렇다.
발표일의 정밀도는 두 가지다: `YYYY-MM-DD` 와 `YYYY-MM`. 후자뿐이라면
우리 추정 구간이 더 많은 것을 말한다.

```
CPI 지수   확정 '2026-08' (월만 앎)   추정 '08/09 ~ 08/15' (24회 중 21회)
```

처음에는 `if 확정: … elif 추정:` 이라 **월 단위 확정이 이기고 추정이 버려졌다.**
가진 정보를 스스로 깎은 것이다. 게다가 정렬키가 `"2026-08"` 이라 `"2026-08-03"`
보다 앞서서, 「다가오는 발표」 맨 앞 세 칸을 `2026-08 중 · 예측 —` 이 차지했다.

지금은 월 단위 확정이면 추정을 쓰되, **추정 월이 확정 월과 다르면 추정을 버린다** —
우리가 아는 사실을 추측으로 덮지 않는다. 월 단위만 남으면 정렬키는 그 달의 말일이다.
카드와 목록은 `useEstimate()` / `use_est` 라는 **같은 규칙**을 쓴다.
한쪽만 고치면 카드가 `2026-08 중`, 위 목록은 `08/09~08/15` 라고 말해 둘 다 못 믿게 된다.

#### 가로 스트립을 주차 묶음으로

12개를 가로로 늘어놓으니 `scrollWidth 1858 / clientWidth 1166` — **넷이 화면 밖**이었다.
그리고 8/07 다음이 곧장 10/25 인 **2.5개월 구멍**이 다른 항목과 똑같은 간격으로 놓였다.
세로로 흐르는 `이번 주 / 다음 주 / 그 이후` 라야 구멍이 구멍으로 보인다.
빈 구간은 헤더째 생략한다. 확정 일정에는 `· 3일 뒤` 를 붙인다 — `2026-08-07` 보다
먼저 읽힌다. 추정 구간에는 붙이지 않는다(구간에는 D-day 라는 개념이 없다).

묶음 기준은 **정렬키와 같다.** 달라지면 그룹이 목록 안에서 연속하지 않게 된다.

**추정 구간이 지났는데 값이 없으면 그 자체가 신호다.** 카드에 `발표 예정일 경과` 가
붙는다 — 발표는 났는데 우리가 못 받았다는 뜻이다. 이 기능을 넣자마자
미시간대 소비자심리가 걸렸다(7월분 예상 7/20~7/30, 최신은 6월). 그 전까지 화면은
이걸 **조용히** 지난달 값으로 보여주고 있었다.

### 「지금 이 값이 높은 건가」

카드와 상세에 `최근 1년 2.4%~4.2% · 5년 내 위치 53/100` 을 함께 적는다.

처음에는 `5년 상위 37%` / `5년 하위 20%` 로 50 에서 말을 뒤집었다. 늘 작은 숫자를
쓰려던 것인데, 그러면 **카드 여덟 장을 훑으며 눈으로 비교할 수가 없다** — 매번 단어를
읽고 머릿속에서 뒤집어야 한다. 한 방향으로만 말한다: 0 = 5년 최저, 100 = 5년 최고.
`위치` 에는 상·하 함의가 없어서, 바닥에 있는 값이 `상위 98%` 로 읽히던 오독도 함께 사라진다.

CPI 지수·PPI 지수에는 **붙이지 않는다.** 물가 수준 지수는 추세적으로 우상향이라
백분위가 언제나 꼭대기다 — 실측으로 최근 24개월 백분위가 CPI 95~98, PPI 93~98 로
**24/24 개월이 90 이상**이었다. 정보가 0인데 정보인 척하는 표시가 된다.

처음에는 `unit == 'index'` 로 걸렀는데 그건 너무 거칠었다. ISM PMI(12~95)와
미시간대 소비자심리(0~65)도 같은 단위지만 오르내리는 서베이 지수라
백분위가 오히려 가장 값진 정보다. 기준은 단위가 아니라 '추세적으로 한 방향인가' 다.

### 없는 데이터를 그리지 않는다

2025-10 은 CPI 발표 자체가 없었다. 그 행을 빼면 표가 12-18 에서 10-24 로 조용히
건너뛰고, 사용자는 데이터가 깨진 줄 안다. 표에는 `2025-10 — 발표 없음` 줄을 넣고
차트는 그 구간만 점선으로 잇는다. **이유는 쓰지 않는다** — 우리가 아는 것은
'그 기준시점의 발표가 없다' 까지이고, 셧다운이라고 단정하면 다른 사유일 때 거짓말이 된다.

### 설명은 터치에서도 열려야 한다

`title` 속성은 마우스에서만 열린다. 화면에 title 이 72곳 있었고 그중 ⓘ 는
'여기 설명이 있다' 고 약속까지 했다 — 모바일 사용자에게는 약속만 있고 내용은 없었다.
마우스 hover · 키보드 focus · 터치 tap 세 경로를 모두 여는 팝오버로 바꿨다.

카드와 타임라인 행은 통째로 `<button>` 이라 그 안의 팁은 **hover 전용**이다.
버튼 안에 초점 받는 요소를 넣는 것은 잘못된 HTML 이고(Chrome 이 초점을 버튼으로
되돌린다), 탭을 가로채면 '카드를 눌렀는데 아무 일도 안 일어나는' 죽은 구역이 생긴다.
같은 설명은 상세 패널에 본문으로 들어 있다.

같은 이유로 카드 안에 `<a>` 를 넣지 않는다. 연준·한은 카드는 발밑에
`정책회의에서 결정` 이라고만 적고, 공식 일정 링크는 상세 패널 각주에 둔다.

서프라이즈 막대의 값 읽기도 SVG `<title>` 이었다 — `title` 속성 72곳을 바꾼
바로 그 이유가 있는데 여기만 남아 있었다. 같은 팝오버로 옮기고 x축 라벨과
`상회`/`하회` 표시를 더했다. 그 전에는 어느 막대가 언제인지 알 길이 없었다.
지금 화면에 `title` 속성은 **0개**다.

### 서프라이즈를 읽는 법

`예상 상회 · 우호적` 처럼 두 단계로 표시한다.

- **1차는 사실이다** — 실제가 예측보다 높았나 낮았나.
- **2차는 성격이다** — 그 방향이 경제활동에 우호적인가.
  실업률이 예상보다 높은 것과 고용이 예상보다 많은 것은 둘 다 '상회' 지만 방향은 반대다.
  `higher_is_better` 가 정의된 지표에만 붙으며, 지표 성격 표시일 뿐 투자 판단이 아니다.

**색은 방향만 나타낸다.** 상승 빨강·하락 파랑은 원본 엑셀에서 계승한 규칙이고,
좋고 나쁨은 다른 축이다. 둘을 같은 색 언어로 섞으면 둘 다 못 읽게 되므로
성격 표시는 중립적인 테두리 배지로 분리했다.

**서프라이즈는 컨센서스와 같은 자릿수로 계산한다.** 예측이 0.1%p 단위인데
실제값만 전체 정밀도로 쓰면 시장이 겪지 않은 서프라이즈가 만들어진다.
위의 [「실제」와 「이전」…](#실제와-이전은-같은-종류의-숫자가-아니다) 절을 참조.

### 비교 보기에서 이중 축을 쓰지 않는 이유

스케일이 다른 두 계열을 한 축에 억지로 얹으면 **없는 상관관계가 눈에 보인다.**
그래서 단위가 같을 때만 겹쳐 그리고, 섞이면 각자 축을 가진 작은 차트로 나눈다.

같은 이유로 **카드 스파크라인은 개수가 아니라 기간(최근 2년)으로 자른다.**
개수 기준이던 때에는 금융 카테고리 안에서 미국 CDS 0.7년과 한국 기준금리 4.3년이,
고용 안에서 1.9년과 5.7년이 같은 폭으로 나란히 놓였다 — 폭이 같은데 기간이 다르면
기울기 비교가 거짓말이 된다.
어느 쪽이든 축은 언제나 하나뿐이다.

그 기간을 전 지표 2년으로 통일한 순간 카드 발밑의 `2024-06 ~ 2026-06` 은
**22장이 같은 문자열을 반복하는 정보량 0** 이 됐다. 규칙은 카드마다가 아니라
화면에 한 번만 적으면 된다(`카드의 작은 그래프는 모두 최근 2년입니다`).

#### 작은 차트에는 x축이 없었다

작은 차트들은 x 도메인을 이미 공유하고 있었는데 — **그 사실이 화면에 안 보였다.**
패널 SVG 의 텍스트가 y 최소·최대 둘뿐이라, 이력이 짧은 계열(ISM 2024-09~)이
오른쪽 끝에 몰려 그려지는 것이 렌더링 오류처럼 읽혔다.

축은 **맨 아래에 하나만** 그린다. 패널마다 반복하면 시끄럽고, 하나면
'이 x 는 모든 패널에 같다' 가 그림 자체로 말해진다. 축이 생기니 선이 없는 구간도
'데이터 없음' 으로 정확히 읽힌다.

기본 범위는 `전체` 가 아니라 `5Y` 다. 36년을 한 화면에 넣으면 COVID 스파이크가
화면을 지배해 최근 몇 년의 움직임이 선 굵기 안으로 사라진다.

색은 순위가 아니라 지표에 붙는다 — 하나를 빼도 남은 지표의 색이 바뀌지 않아야
이전에 본 화면과 비교할 수 있다.

## 자동화가 얻어낸 것

- **개정(revision) 추적** — 같은 기준월의 값이 바뀌면 `revisions` 에 기록된다.
  NFP 처럼 두 번 개정되는 지표의 수정 폭이 보인다.
- **발표 당시 값과 현재 값의 구분** — FRED vintage(`output_type=4`)로 최초발표값을,
  기본 조회로 개정된 현재값을 따로 가져온다. 전자는 `releases.actual`,
  후자는 `observations` 에 들어간다.
- **발표일과 기준월의 분리** — 엑셀은 둘이 섞여 아래 오류가 생겼다.
- **이벤트 발표일 병합** — 같은 FOMC 를 엑셀은 한국 날짜(07-30),
  캘린더는 미국 현지(07-29 14:00 ET)로 준다. 더 이른 날짜로 자동 병합한다.
- **계절조정 여부 검증** — `require_seasonal_adjustment` 가 걸린 지표는 수집 전에
  FRED 계열 메타데이터를 조회해 실제로 그런지 확인한다. 계열 ID 만 봐서는
  알 수 없는 사실이라 믿음이 아니라 코드가 보장하게 했다.
- **ISM 역사 복구** — 캘린더 웹페이지의 과거 주 조회로 ISM 2종을 2019-12 까지 채웠다.
  엑셀 백필은 2024-09 부터였다. 백필은 **빈 칸만 채우므로**(`fill_only`) 엑셀에서 온
  발표 당시 컨센서스는 한 건도 바뀌지 않는다.

### 매핑 검증 (2026-08-01)

```bash
python scripts/verify.py --offline     # API 키 없이 커밋된 데이터로 검증
```

엑셀 값은 이제 **독립적인 제3의 대조군**으로만 쓴다 — 손으로 다른 출처에서 옮겨 적은
값이므로, FRED 값과 맞으면 계열 매핑이 옳다는 증거가 된다.
그 결과 FRED 계열 12종 중 **11종의 매핑이 확인**되었다.

| 판정 | 지표 | 의미 |
|---|---|---|
| 정확 일치 100% | CPI 지수, CPI YoY, 미국 기준금리 | 완전 일치 |
| 개정 차이 | PPI, PCE, 근원 PCE, NFP, 실업률, 시간당 임금, 신규 실업수당, JOLTS | 매핑 정상 |
| **조사 필요** | 10Y-2Y 금리차 | 아래 참조 |

**'개정 차이'는 정상이다.** 엑셀에는 *발표 당시* 값이, FRED 에는 *개정된 현재* 값이 들어 있다.
NFP 는 두 번 개정되므로 정확 일치율이 2% 인 게 오히려 맞다 — 차이의 중앙값이 67천명으로
통상 개정 폭(`revision_band=200`) 안에 있으므로 매핑은 옳다.
`verify.py` 는 정확 일치율만 보지 않고 이 폭과 비교해 판정한다.

**10Y-2Y 만 개정으로 설명되지 않았다.** 시장금리는 개정되지 않기 때문이다(`revision_band=0`).
원인을 추적한 결과 **엑셀 쪽 날짜가 어긋나 있었다**:
엑셀에는 2026-07-03, 2026-06-19 에 값이 있는데 이 날들은 미국 휴장일이라 FRED 에 호가 자체가 없다.
엑셀의 값들은 FRED 에 존재하지만 라벨과 다른 날짜에 붙어 있다.

### 제거한 엑셀 실제값 (`scripts/prune_excel_actuals.py`)

처음에는 '자동 소스가 있으면 엑셀 실제값을 전부 지운다'는 규칙을 세웠다.
**실제 데이터로 확인해 보니 그 규칙은 멀쩡한 데이터를 442건이나 지웠다.**

- 신규 실업수당: 엑셀 187 vs FRED 현재값 188 은 오염이 아니라 **개정**이다.
  FRED vintage 가 최초발표값을 187 로 확인해 준다.
- 기준금리: 엑셀 행은 금리가 바뀌지 않은 FOMC·금통위 날짜다. 값 충돌 0건이고,
  자동 소스에는 없는 '회의가 열렸다'는 정보를 더한다.

그래서 규칙을 좁혔다 — **권위 있는 소스가 그 날짜에 값을 갖고 있지 않은 행만 지운다.**
날짜 자체가 틀렸다는 뜻이기 때문이다. 실제 제거는 8건뿐이었다.

| 지표 | 제거 | 이유 |
|---|---|---|
| 10Y-2Y | 2건 | `2026-07-03`, `2026-06-19` — 미국 휴장일이라 FRED 에 호가 없음 |
| 미국 CDS | 4건 | worldgovernmentbonds 이력에 없는 날짜 |
| 한국 CDS | 2건 | 동일 |

제거 후 10Y-2Y 는 남은 5건이 FRED 와 **100% 일치**한다.
PPI 는 별도 제거가 필요 없었다 — 계절조정 계열로 고치자 FRED 값이 전부 덮어썼다.

**예측·이전은 전 지표에서 보존했다(429건 / 8,858건).** 스크립트가 실행 전후 건수를
대조해 줄어들면 실패로 처리한다 — 복구 불가능한 데이터이기 때문이다.

## 자동 실행

`.github/workflows/시황-수집.yml` 이 세 가지 계기로 돈다.

| 계기 | 하는 일 |
|---|---|
| 하루 두 번 (09:10 / 21:10 UTC) | 수집 → CSV 커밋 → 배포 |
| `main` 에 push | 코드 변경을 즉시 배포 (`data/**`, `site/data/**`, `*.md` 제외) |
| 수동 실행 | 소스 지정·CDS 건너뛰기 가능 |

push 트리거가 없던 동안 **코드를 고쳐도 사이트가 갱신되지 않는** 문제가 있었다.
`paths-ignore` 에 봇이 커밋하는 경로를 모두 넣어야 무한 루프가 나지 않는다 —
`data/**` 만 넣으면 `site/data/dashboard.json` 커밋이 워크플로를 다시 부른다.

## GitHub Actions 배포

이 폴더는 아직 git 저장소가 아니다. 먼저 초기화하고 올린다.

```bash
git init
git add .
git commit -m "매크로 지표 대시보드 초기 구성"
git remote add origin https://github.com/<계정>/<저장소>.git
git push -u origin main
```

그다음:

1. 저장소 Settings → Secrets and variables → Actions 에 `FRED_API_KEY`, `ECOS_API_KEY` 등록
2. Settings → Pages → Source 를 **GitHub Actions** 로 설정
3. `.github/workflows/시황-수집.yml` 이 하루 두 번(09:10 / 21:10 UTC = 18:10 / 06:10 KST)
   수집 → CSV 커밋 → Pages 배포

Actions 러너는 매번 빈 상태로 시작하지만, `db.connect()` 가 커밋된 CSV 에서 자동 복원하므로
이력이 끊기지 않는다.

수동 실행은 Actions 탭에서 `workflow_dispatch` 로. 특정 소스만 돌리거나 CDS 를 건너뛸 수 있다.

## 자동 수집이 실패했을 때

`manual_overrides` 테이블에 넣은 값이 자동 수집값보다 항상 우선한다.

```sql
INSERT INTO manual_overrides (series_id, ref_date, field, value, reason, created_at)
VALUES ('ism_manufacturing', '2026-07-01', 'actual', 53.3, 'ISM 사이트에서 직접 확인', datetime('now'));
```

`scripts/collect.py` 가 마지막 단계에서 반영하며, 대시보드 표에 `수동` 태그가 붙는다.
`data/manual_overrides.csv` 를 직접 편집해도 된다 — 그쪽이 영속 형식이다.

이 경로가 실제로 필요해지는 경우는 하나다: **ISM 2종의 스크레이핑이 막혔을 때.**
나머지 지표는 FRED·ECOS 가 언제든 다시 주므로 다음 실행이 알아서 메운다.
`verify.py --stale` 이 멈춘 계열을 알려주므로, 거기 ISM 이 뜨면 이 경로를 쓸 때다.

## 알려진 한계

- **ISM 실제값은 스크레이핑에 의존한다.** 공식 피드가 실제값을 주지 않고 FRED 에도 없어
  대안이 없다(위의 후보 표 참조). 페이지 구조가 바뀌거나 Cloudflare 가 GitHub Actions IP
  를 막으면 끊긴다. 끊기면 `verify.py --stale` 과 카드의 `N개월째 갱신 없음` 이 알려주고,
  `manual_overrides` 로 메울 수 있다. **조용히 죽는 경우만 없게 해 뒀다.**
  - 이전 판 README 는 여기에 "ISM 이 피드에 잡히는지는 발표 후 확인이 필요하다" 고
    적어 두고 그 확인을 아무도 하지 않았다. 두 달간 못 잡힌 이유다.
    지금은 사람이 기억할 일이 아니라 검사가 할 일이다.
  - 매핑 오타 대비는 그대로다 — `ff_aliases` 가 옛 이름(`ISM Non-Manufacturing PMI`)도
    색인하고, 못 잡으면 `suggest_mappings()` 가 유사 제목을 제시한다.
- **미시간대 소비자심리는 FRED 원본이 밀려 있다.** 우리 수집 문제가 아니다 —
  `fredgraph.csv?id=UMCSENT` 를 직접 받아 봐도 2026-06 에서 멈춰 있다.
  정체 감지가 이걸 잡아 화면에 표시한다.
- CDS 는 페이지 구조 변경에 취약하다. 실패는 화면에 표시되며 수동 입력으로 메울 수 있다.
- ForexFactory 는 비공식 소스다. 형식이 바뀌면 수집이 실패하고 값은 갱신되지 않는다
  (잘못된 값이 들어가지는 않는다).
- **GitHub Actions 스케줄은 정시성이 없다.** 실측 지연 3~12시간. 설계가 특정 시각에
  의존하지 않게 두는 것 외에 할 수 있는 일이 없다.
